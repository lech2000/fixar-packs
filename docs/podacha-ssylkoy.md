# Подача ссылкой на выпуск GitHub — основной путь

Манифест подаётся в API точно так же, как при подаче через API ([`podacha-api.md`](podacha-api.md)). Отличается только то, как
площадка получает архив: вместо загрузки байт через карантинную корзину
площадка сама забирает файл из **выпуска (release) на GitHub** — по ссылке и
отпечатку, одним вызовом.

Шаги 1–5 из [`docs/podacha-api.md`](podacha-api.md) (вход, повышение доверия,
заявление документов, заявка издателя и её допуск) — те же самые, здесь не
повторяются.

## Где разместить архив: два варианта

### Вариант 1 — свой открытый репозиторий (основной путь)

Ничего специфичного площадка не требует от вашего репозитория, кроме того,
что он **публичный** и выпуск **опубликован** (не черновик). Проще всего
скопировать себе из этого репозитория `tools/pack.py` и
`.github/workflows/release.yml` — тот же инструмент сборки и та же схема
метки, — и в своём репозитории:

```bash
python3 tools/pack.py build packs/<ns>/<name> --out dist
python3 tools/pack.py tag packs/<ns>/<name>
git tag "$(python3 tools/pack.py tag packs/<ns>/<name>)"
git push origin "$(python3 tools/pack.py tag packs/<ns>/<name>)"
```

— и опубликовать `dist/<ns>-<name>-<version>.tar.gz` как файл выпуска под
этой меткой (руками или тем же `release.yml`, скопированным к себе).

### Вариант 2 — PR в этот репозиторий

Второй путь — для примеров, которые площадка показывает от своего имени, и
для тех, кто не хочет вести свой репозиторий.

1. Открываете PR с паком в `packs/<namespace>/<name>/` — правила приёма в
   [`CONTRIBUTING.md`](../CONTRIBUTING.md).
2. После проверки и слияния сопровождающий репозитория ставит метку выпуска
   по схеме `namespace.name@version` (см. [`docs/format.md`](format.md#метка-выпуска) и
   `python3 tools/pack.py tag packs/<ns>/<name>`).
3. `.github/workflows/release.yml` по этой метке собирает архив
   (`tools/pack.py build`) и публикует его как файл выпуска на GitHub.

Метку и сам релиз в этом репозитории ставят только сопровождающие — не
автор пака (подробности в `CONTRIBUTING.md`).

## Забрать архив по ссылке

Дальше, независимо от варианта — подать версию, как при подаче через API:

```bash
jq -n --rawfile y packs/acme/inbox/pack.yaml --arg pid "$FIXAR_PRINCIPAL" \
  '{principal_id: $pid, pack_yaml: $y}' \
  | curl -s -X POST https://api.agrigate.pro/registry/versions \
      -H "Authorization: Bearer $FIXAR_TOKEN" \
      -H 'Content-Type: application/json' --data-binary @-
```

```bash
export FIXAR_VERSION_ID=<id из ответа>
```

И одним вызовом отдать площадке ссылку на файл выпуска и его отпечаток:

```bash
curl -s -X POST https://api.agrigate.pro/registry/artifacts/from-github \
  -H "Authorization: Bearer $FIXAR_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "principal_id": "'"$FIXAR_PRINCIPAL"'",
    "version_id": "'"$FIXAR_VERSION_ID"'",
    "url": "https://github.com/<owner>/<repo>/releases/download/acme.inbox@1.0.0/acme-inbox-1.0.0.tar.gz",
    "declared_digest": "<sha256 из вывода tools/pack.py build>"
  }'
```

Шаги «upload-url → PUT → finalize» здесь не нужны: площадка сама скачивает
файл, сверяет отпечаток и отдаёт архив сканеру в этом одном вызове. Ответ — тот же формат артефакта, что у
`finalize`: состояние (`scan_passed`/`scan_failed`), отчёт сканера,
`source_url`.

Дальше — как при подаче через API: отслеживание через кабинет, `GET
/registry/publishers/{principal_id}/versions` или ящик уведомлений, при
необходимости — отзыв версии (`POST /registry/versions/{id}/yank`).

То же самое, без единого `curl`, делает кабинет автора
(`https://agrigate.pro/pak/kabinet/`) — там достаточно вставить ссылку на
выпуск и отпечаток в форму: внутри она вызывает ту же ручку
`/registry/artifacts/from-github`.

## Что именно принимается по ссылке

Площадка принимает ссылку **строго** вида:

```
https://github.com/<owner>/<repo>/releases/download/<метка>/<файл>.tar.gz
```

— то есть файл, приложенный к **опубликованному** выпуску (release) на
GitHub. Не принимаются: черновик релиза (draft), приватный репозиторий,
произвольный URL, зеркало или CDN стороннего сервиса. Площадка сама проходит
переадресации, но разрешает их только на серверы, которые действительно
принадлежат GitHub, — и отказывает, если переадресация ведёт куда-то ещё.
Предел размера архива — 5 МБ сжатого. Площадка проверяет его и по заголовку
ответа GitHub, и по числу реально прочитанных байт.

## Почему отпечаток (`declared_digest`) обязателен

Ссылка сообщает площадке, ГДЕ архив, а не ЧТО в нём лежит. `declared_digest`
— это sha256, который вы сами получили от `tools/pack.py build` при сборке
своего архива. Площадка скачивает файл по ссылке и сверяет настоящий
отпечаток скачанных байт с этим заявленным значением **до того**, как отдаёт
содержимое сканеру: не совпало — содержимое не разбирается вовсе. Это
единственный способ площадки убедиться, что по ссылке лежит именно тот
архив, который вы собрали и проверили локально, а не что-то, подменённое по
дороге или в самом выпуске.

Опечатка в отпечатке не сжигает версию сама по себе — но только при первой
попытке (пока для этой версии ещё не заведён ни один артефакт): несовпадение
ничего не пишет в базу, версия остаётся неразобранной, и вызов можно повторить
с верным `declared_digest`. Если для версии артефакт уже был заведён —
отпечаток для него неизменяем, и придётся подавать новую версию.

## Почему нельзя перезаливать файл выпуска

Отпечаток, который площадка сохранила для версии, неизменяем: одна версия —
один архив, навсегда. Если вы замените файл в уже использованном выпуске
GitHub (тот же тег, другие байты), это не «правка» — по правилам площадки
другое содержимое — это уже следующая версия пака, а не тот же номер. Заново
позвать `from-github` с той же ссылкой для той же версии либо ничего не
изменит (отпечаток совпадал и раньше), либо вернёт отказ о несовпадении, если
файл действительно стал другим. Нужен новый архив — выпускайте новую версию
пака с новым номером и новой меткой.
